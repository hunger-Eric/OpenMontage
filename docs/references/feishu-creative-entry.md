# 飞书统一视频创作入口

飞书通过自然语言和可信附件提交需求，OpenMontage 负责理解、拆解、编排、
生成与合成。适用于新作品、只做分析／方案和继续修改；同样适用于本地入口。
沿用现有流水线、工具、审批、工件和交付协议，不新增业务路由程序。

需要视觉策划的视频请求复用[平台中立视觉视频策划流程](visual-video-planning.md)：
参考资产用于保持人物、产品、场景和风格的可复用特征；镜头关键画面只在需要时用于锁定
实际起始构图或交互状态；动态提示词说明主体、摄影机和环境如何随时间变化。这个逻辑
同时服务自动成片和人工交接，人工交接仍不选择或发现视频平台。
“只要方案”只改变执行的终点和最终交付形式，不跳过原流水线前期工作：按已有 manifest 和 director
执行研究、方案、脚本、分镜，再准备必要参考素材；复用有效工件，保留原审批和检查记录。
阶段成果留在同一工程，最终映射为独立的视频方案看板，不为飞书另写一套策划流程或过程页面。

## 一次说明需求，材料可以混用

先理解用户想得到什么，再判断每份材料的用途。不要仅凭 URL、文件扩展名
或中文关键词选择制作流程，也不要要求用户先选择四种互斥模式。

| 用户需求示例 | 制作路径 |
|---|---|
| 拆解这个链接，再为我的产品制作一条视频 | 取得实际参考媒体，按[参考分析流程](../../skills/meta/video-reference-analyst.md)拆解，再按[参考交接](../../skills/meta/reference-production-handoff.md)改编和制作 |
| 帮我复刻这个视频，参考它的节奏、音色、构图或讲解方式 | 按同一参考交接记录要保留的表达维度与要改变的内容，沿用具体制作语法，为用户自己的内容制作；不因“复刻”一词锁死源时间线，不强行换风格来追求差异 |
| 内容、镜头顺序和时长保持原样，忠实重建画面 | 使用严格复刻契约，冻结明确要求保留的源内容、顺序、节奏及授权品牌／原声；逐段绑定实际视频参考，经既有生产和 Remotion 合成入口执行 |
| 按下面脚本制作，台词保持原文 | 将用户脚本作为内容依据，设计表演、镜头与剪辑；逐字保留要求不得被改写 |
| 根据这组场景图生成视频 | 按用户要求将图片用作场景、外形或风格参考，或原样入片；需要动态镜头时使用实际视频生成路径 |
| 用我的素材剪辑，缺少的镜头用 AI 补 | 先检查原素材，再列出实际缺口，只补必要镜头并合成；必用素材不能被相似生成素材替换 |
| 我有个产品叫 X，帮我写一份视频方案 | 走[人工生成方案工作流](manual-video-handoff.md)，在飞书新建该项目独立的[视频方案多维表格](feishu-video-plan-base.md)，包含总览、带实际图片附件的参考资产、与资产真实关联的生成片段、图序用途、口播／对白、屏幕文字和完整提示词；本地请求或明确要求 Word 时使用 DOCX，明确要求 Excel 时使用 XLSX；以后回传视频再复用当前项目继续后期 |
| 我有个产品叫 X，帮我写一份视频文案 | 只交付文字文案，不生成参考图或视频；点名视频技能不改变这个范围 |

同一作品可以同时有参考链接、用户脚本、人物／产品／场景图、实拍视频和音频。
角色与产品外形、叙事风格、场景参考和必须原样入片的素材分别说明。
某份材料可有多个用途；未明确且会影响结果的用途需要询问，不能默默替换。

## 少问，但不扩大制作范围

- 用一段简短摘要说明理解到的目标、材料用途、保留项和本次交付。
  不要求用户填写完整表单，也不把内部模型、引擎或混音参数当作必答项。
- 复用会话中已确认的时长、画幅、声线、音乐和生成路径。没有固定全项目
  时长、比例、镜头数或声音预设；可根据用途提出合理选择，标明推断。
- 只询问会实质改变结果、权限或范围的缺口。信息已经足够时继续完成；
  不把简短理解摘要变成额外审批门。沿用实际流水线和现有用户授权。
- “视频文案”只交付文字，不生成参考图或视频；不需要用户额外强调“只要文字”。
  “只拆解”“只要文字”“先构思方向”按相应范围交付，不生成素材。
  “帮我写一份视频方案”默认按生成片段组织，每段一组必要参考图和一条完整提示词，
  几秒的分镜／动作节奏写在该段提示词内，不自动拆成单独生成任务。
  在飞书中，每个生成片段一条记录，关联所需参考资产记录，并保留图序与用途、场景、画面动作、
  口播／对白、屏幕文字和完整提示词；只通过原话题既有结果返回独立看板网页链接，不自行发送群消息。
  原图在工程内保留复用。不生成视频；
  不要求用户先说“人工生成”、枚举交付物或填完整表单。也可以直接说：
  “使用 ai-video-gen 技能。我有个产品叫 X，帮我写一份视频方案。”明确只要文字时仍只交付文字。
  使用现有图像工具准备必要参考图。方案只写构图、动作和镜头要求，
  不指定视频模型或平台、不要求视频提供方发现；员工自行选择生成方式。
  产品图、真人／动漫／拟人角色图和不同主场景的场景图按实际需要设计或复用，
  不固定两张，也不为每个小动作重新生成。飞书 Base 的参考资产记录上传实际图片附件、
  编号、视觉设定、用途和关联片段；各生成片段记录及完整提示词逐段对应所用编号、
  图序和各图约束。Base 显示图片不等于已经进入视频模型；后续仍需按适配器真实字段上传并核对回执。必要图缺失时明确保留缺口，不把文字描述或占位格当作完成。
  “拆解并生成”“按脚本制作”“直接做成片”按明确范围持续完成。
  “可以”之类回复按其所回应的问题和已有授权理解，不能统一当作制作授权。
- 用户要求保留脚本、原声、人物或实拍素材时优先遵守；不为匹配工具模板
  改写台词或更换素材。不假定收到的每张图都要原样入片或都要重新生成。

## 收齐材料，再开始制作

单条文字／链接、或同一消息中已完整提供的图片与说明可直接交给现有入口。
非图片文件、混合附件或分多条上传，只有在本轮实际确认素材窗口能力并取得有效窗口回执后，才能沿用 Bridge 的素材收集窗口：

```text
@机器人 /素材开始 用我上传的实拍视频和产品图制作宣传片，缺少的镜头用 AI 补。
（按需继续上传图片、视频、脚本文件或音频，并补充说明）
@机器人 /素材结束
```

普通同条 mixed post 可直接使用其中的已冻结附件，不依赖 legacy 素材窗口。分多条上传若没有有效 OPEN/CLOSE 窗口回执，不启动制作并报告传输缺口。结束上传前不抢先启动制作。使用本轮冻结后的附件身份、实际文件和任务说明；
登记已收到的材料和实际缺口，不把消息预览、下载回执或同名文件当作完整素材。
未来的“开始收集／上传完成”按钮只能替代上述传输动作，不接管业务判断；
当前仍以实际已实现的命令和窗口回执为准，不能仅凭普通消息已送达推断窗口已开启或关闭。

公网视频链接由 OpenMontage 的现有参考获取路径处理，不能假定 Bridge 已下载。
获取失败保留明确原因；没有实际媒体时不能声称已经拆解了画面和声音。

## 同一作品继续改，新增材料不等于新作品

建议每项作品使用一个飞书话题。用户在原话题明确说“继续上一版，只改……”
或“给上一版补充这些素材”时，沿用已知项目、已接受素材、分析和创作决定。
记录本次保留项与变化；只修相关部分，新版本保留原版本。

方案里展示的参考图仍需作为实际生成输入：按片段复用工程中已登记的原图，
按选定适配器的真实字段传入，并核对上传／关联回执。必要参考图未绑定时不提交无图生成；
Base 中显示图片、文档内嵌图片、提示词提到图片或生成成功，都不能证明图片已进入模型。
多维表格 API 或权限缺失时保留已规划内容并返回具体错误，不静默退回 Word；适配器只负责记录附件与字段传输，不改变创意内容或视频提供方选择。

在 `scene_plan` 阶段将完整方案及必要实际参考图整理为独立看板，经既有 Worker 返回原话题，
等待用户确认该方案版本；后台继续显示阶段与工件。不默认制作十秒样片，也不在素材生成后
再次等待人工确认。方案获批后按自动／人工选择执行整片或接收回传，内部质量验收不省略。

Bridge 的任务／会话连续性是传输依据，OpenMontage 的项目工件是制作依据。
新附件仍按本轮固定；历史内容只通过当前执行器提供的可信引用或
`prior_artifact` 身份复用，核对项目归属、资产 ID、来源工件与实际文件哈希。
相同哈希、相似文件名或“以前传过”本身不建立信任，也不能扩大可访问目录。
仅有旧路径而没有有效身份、项目上下文或访问权限时，保留缺口并询问准确引用。

用户明确要求新作品时建立新的项目关系，不隐式覆盖原作品。多个候选作品
存在歧义时只问要继续哪一个；不扫描别的工作区猜素材。复用现有排队、任务
身份和恢复机制，未知生成继续核对原提交，重复消息不重复提交付费任务。

## 沿用工件和执行职责

### 按已确认方案准备素材

Agent 在设计方案时判断是否需要统一处理素材，向客户说明处理意图；方案确认后再执行。
具体处理方式和工具由 agent 根据实际素材与制作需求选择，不固定步骤、参数或格式。
上传本身不触发处理，不重复处理已符合要求的素材；保留原件和必要处理记录，继续原有剪辑流程。
已有 `media_prepare` 可供基础处理使用，不要求所有处理都走这个工具，也不追加审批节点。

不另建一套可变任务状态或专用 Bridge 消息 JSON 协议。原生 Base 工具的入参只投影已确定的
方案内容；可信素材、生产工件和原话题结果协议继续沿用。制作请求的简短理解摘要、材料用途、
保留项和变化可放在拥有该决策的 `brief`／`proposal_packet` 的
`metadata.creative_request` 中；只保存一次，后续通过工件引用继承。
它是模型的交接说明，不是程序自动分流或执行证明。实际资产、哈希、生成身份
仍以 `asset_manifest`、来源回执与原始工件为准；剪辑、渲染和交付沿用各自工件。
仅分析的任务交付其真实分析结果，不伪造生产阶段或审批记录。

| 关键职责 | 执行者 | 边界与证据 |
|---|---|---|
| 接收、附件固定、任务身份与续聊 | Bridge／Worker 代码 | 现有冻结回执、任务输入及会话映射；不按视频关键词选择流程 |
| 目标、材料用途、续改与镜头缺口判断 | Codex 模型 | 用户请求、可信上下文和权威项目工件；不能用规则匹配替代语义判断 |
| 生成需要的新素材 | 已批准的图像／视频／语音模型 | 实际请求与提供方回执；工具在当前 Worker 中不可用时明确报告缺口 |
| 音频处理、剪辑合成、身份与格式校验 | 项目工具代码 | 实际输入、输出及验证回执；不替代创作判断、不暗换画面 runtime |
| 创作验收与飞书交付 | Codex 判断；Worker 验证与交付代码 | 实际成片证据与交付身份；看不到或听不到的效果保留未验证 |

前期的目标、脚本、角色、场景和必用素材保持为同一套项目工件；在最终镜头
全自动生成处通过 `video_selector` 和[提供方扩展接口](video-provider-extension.md)
接入 MCP 或 API。具体模型的支持范围、参数映射和提交回执由适配器负责，
不因更换接入方式重新建立创作流程，也不假定尚未接入的 API 已可用。

新作品的主合成运行时默认锁定 `remotion`，不要求用户选择 Remotion／Hyperframes。
FFmpeg 继续承担必要的音频处理、剪辑和封装，不作为默认技术菜单中的另一选项。
已有作品沿用其明确的运行时记录；Remotion 不可用或既有运行时失败时报告缺口，
不能静默换引擎。技术身份保留在工件与回执中，不显示在视频画面中。

Google Omni / Flow 人物口播沿用[中文换声规则](omni-chinese-redub.md)：
只有纯中文换配音并对齐，英文与混合语言保留原声并跳过专项。
背景音乐沿用[音乐工作流](music-workflow.md)，最终合成带入其中的
[制作提示](music-workflow.md#最终制作提示)，不把制作说明显示在画面中。

## 接入与验收

飞书 Worker 可以从其他工作区启动；入口必须指向本项目权威技能，
不要求用户填写本机目录，不在 Bridge 中复制提供方配置或视频技能实现。
技能存在、发现列表、工具可用、真实执行与飞书交付分别记录证据。

本地检查只验证链接、工件 schema 和传输边界；真实验收需在飞书分别提交
上述四类请求，并覆盖混合材料、只分析、原话题续改及新增材料。
保留来源、项目关系、素材和成片证据，核对实际回传；未完成的真实路径不得
用模拟测试或本地成片宣称通过。部署、外部消息及新媒体生成沿用实际授权。
